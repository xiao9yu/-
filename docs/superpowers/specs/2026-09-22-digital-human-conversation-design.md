# 数字人交互增量迭代设计（2026-09-22）

## 0. 为什么做这三件事

09-20 的 Plan E 把"语音问答 → 分句朗读 → Live2D 音量驱动口型"这条链路跑通了，但它停在
"能演示"：**数字人不会追问、用户必须按住说话、口型只跟音量走**。这三条恰好是评审与答辩
最容易一眼看出差距的地方。本次迭代逐条补齐，并明确各自的**能力边界**（做到哪、没做到哪）。

| 迭代项 | 之前 | 现在 | 仍未做到 |
|---|---|---|---|
| 对话 | V1 单轮，不存历史 | 多轮会话落库 + 上下文进提示词 + 追问检索改写 + 历史引用回放 | 无长期记忆提炼、无跨会话主题归纳 |
| 语音 | 按住说话，整段转写（10s 语音约 5s 出字） | 服务端 FSMN-VAD 自动断句 + paraformer 流式增量转写（边说边上屏） | 不做全双工（播报时不听，避免自问自答） |
| 口型 | 音量包络 → 开口度 | edge-tts WordBoundary 时间轴 → 音节级张合（标点处闭嘴） | 幅度仍是启发式，**不是音素级 viseme** |

## 1. 多轮会话（本周项 ①）

### 1.1 数据模型

`app/models/chat.py`：`chat_sessions`（id / user_id / title / turns / 时间戳）+
`chat_messages`（id / session_id / role / content / citations JSON）。

为什么落库而不是只存前端内存：WS 语音链路断线最多重连 3 次、用户会刷页面，上下文必须在
服务端；而且 `citations` 随轮次落库后，"引用延续"才是真的——历史轮次的溯源不会因为翻页丢掉。

### 1.2 上下文如何进提示词

`chat_service.recent_history()` 取最近 3 轮（问+答）→ `rag_ask.build_answer_prompt(history=...)`
把它们作为正式对话消息插在 `system` 与当前 `user` 之间，并在 system 追加「对话历史」提示。

**历史里的 `[n]` 引用编号会被剥离**：提示词里的资料编号每轮重新从 `[1]` 起编，带旧编号进上下文
会被模型当成"已存在的资料"引用，产生指向错误的溯源。

### 1.3 追问检索改写（rewrite_query）

"那它设大了会怎样"这类指代型追问，直接拿去检索是零信息查询，必然空手。处理方式：

- 触发条件：问句 ≤14 字，**或**命中指代/承接词（它 / 这个 / 该 / 上述 / 继续 / 还有 / 为什么 / 举个例子 …）；
- 动作：把**上一轮用户问题**与当前问句拼接作为检索 query（提示词仍用原问句）。

为什么不用 LLM 改写：改写要多一次 LLM 往返（首字 1~2s），而语音链路对首响延迟极敏感；
多轮 RAG 里指代对象的落点几乎总在"上一轮用户问题"，拼接是零延迟、可解释的近似。
代价是并发多主题时可能引入噪声命中，由 bge-reranker 精排兜住。

### 1.4 接口

- `POST /api/kb/ask {question, session_id?}`：SSE 首帧恒为 `session` 事件（`{id, turns}`）；
  `session_id` 传空/无效则新建（静默，不打断提问）。
- `GET /api/chat/sessions`｜`GET /api/chat/sessions/{id}/messages`｜`DELETE /api/chat/sessions/{id}`（仅本人，越权返回 404 不区分）。
- WS `auth {token, session_id?}`：语音与文字**共享同一条会话**，混用不丢上文；服务端每轮回 `session` 事件。

## 2. 流式自然对话（本周项 ②）

### 2.1 为什么端点检测放在服务端

浏览器侧 RMS 阈值法 VAD 需要手调阈值，对风扇/键盘噪声误触发，对轻声起头不敏感。
本机 modelscope 缓存里已有 `iic/speech_fsmn_vad_zh-cn-16k-common-pytorch`（FSMN-VAD，
训练出来的端点模型），因此改为**前端只负责送干净数据、服务端判端点**：少一个需要调的参数，
且鲁棒性不在一个量级。前端仅在播报期间停止送帧（省带宽与 CPU，后端同样会丢弃）。

### 2.2 模型与粒度

| 环节 | 模型 | 粒度 |
|---|---|---|
| 端点检测 | `fsmn-vad`（FSMN-VAD） | 流式固定 200ms |
| 增量转写 | `paraformer-zh-streaming`（online paraformer） | 流式固定 600ms（`chunk_size=[0,10,5]`） |

两者都由 `app/services/asr_stream.py` 内部缓冲对齐，调用方（WS）可按任意帧长喂入。

### 2.3 状态机与降级

`StreamingRecognizer.feed(pcm16) -> [(事件, 数据)]`，事件为 `partial` / `segment_end`：

- 段首预滚 300ms：VAD 判定"起说"时补回此前音频，避免吃掉字头（段尾不需补偿，FSMN-VAD 自带 hangover）；
- 段落内按 600ms 步长喂流式 ASR → 出 `partial`（边说边上屏）；
- VAD 判定端点 → 冲 ASR 尾帧（`is_final=True`）→ 出 `segment_end`（含段时长）；
- **降级**：流式 ASR 不可用而 VAD 可用 → 段末回退批量 `transcribe`（同一进程已缓存批量模型）；
  VAD 也不可用 → `available()=False`，前端不展示"自然对话"入口，退回按住说话。

`available()` 只看**已加载**状态、不触发加载：它在事件循环里被调用，原地加载 880MB 流式 ASR
会阻塞整个 loop。加载交给启动预热线程（`main.py::_preheat_models`）。

### 2.4 WS 协议增量

| 方向 | 消息 | 说明 |
|---|---|---|
| C→S | `stream_start` / `stream_chunk {data: PCM16 16k}` / `stream_end` | 自然对话 |
| C→S | `interrupt` | 只中断本轮回答（抢话），监听继续 |
| C→S | `cancel` | 结束整场会话（按住说话路径整轮取消） |
| S→C | `status listening` / `partial` | 监听中 / 增量转写 |
| S→C | `segment_done` | 单个语音段播报完毕，会话不结束 |

**不做全双工**：扬声器播报会被麦克风收回形成自问自答，浏览器回声消除不保证干净，
因此选择"朵娅说话时不听"这一保守但可用的策略（前端不送帧 + 后端丢弃帧，双保险）。

## 3. 口型时间轴（本周项 ③）

### 3.1 时间轴从哪来

`tts_service._communicate_timed()` 以 `boundary="WordBoundary"` 请求 edge-tts，收集
`WordBoundary` 分片（offset/duration，100ns 单位）→ 与 mp3 一起下发（WS `audio.marks`、
HTTP `POST /api/voice/tts/timed`）。

字节路径（`synthesize` / `_communicate`）与口型路径（`synthesize_timed` / `_communicate_timed`）
**各自独立缓存、互不污染**：口型路径命中缓存时时间轴不能是空的。

### 3.2 前端如何驱动

`utils/lipsync.ts`：

1. **词级 → 音节级**：中文 WordBoundary 按词切分，一个词的时窗按字符数均分；
   "梯度下降"因此得到两次开合而非一次长张。
2. **单音节包络**：音节时窗内走 `sin(πu)` 半波（张口 → 最大 → 闭口）；
   标点/空白音节 `open = 0` → **停顿处闭嘴**，这是观感提升最明显的一处。
3. **幅度**：字符散列取 [0.55, 1.0] 的**稳定**值（同一字每帧一致，否则口型会抖），
   长词略宽。
4. **合成最终值**：`音节包络 × (0.35 + 0.65 × 音量门限)`——包络决定"何时张口、张多大"，
   实时音量决定"这一刻是否真在出声"，两者相乘使时间轴错位或静音段都不会凭空张合。
   拿不到 marks（服务端不下发边界）则自动退回纯音量驱动。
5. `MouthEnvelope` 用**游标**而非逐帧全扫查表（长回答有几百个音节，逐帧线性扫描白烧 CPU）。

`PlaybackManager.onMouth` 每帧输出最终值；`Live2DAvatar` 经 `afterMotionUpdate` 写入
`ParamMouthOpenY`（快开慢合低通 0.6/0.3）。

### 3.3 能力边界（答辩要主动说明）

当前是**音节级时间对齐 + 启发式开合幅度**，不是音素级视位（viseme）。
做真视位需要拼音/音素词典把韵母映射到口型分组（a/o/e 大开、i 扁、u/ü 圆小、b/p/m 闭唇）。
下一步用 `pypinyin`（需新增依赖）或内置韵母表即可升级，时间轴基础设施已就位。

## 4. 前端可感知的变化

- 头部：`第 N 轮 · 记得上文` 标签、`历史对话` 抽屉（会话列表 + 删除）、`新对话`。
- 输入区：`自然对话` 开关（服务端能力就绪才出现，否则是原`按住说话`）；
  自然对话中按钮变`结束对话`，`打断`只掐本轮播报、监听继续。
- 气泡：监听中显示`正在听`标签与实时 partial 文本；续接历史时提示"我记着上文"。
- 历史会话点开即续接：载入最后一轮问答 + 引用，下一句提问带上完整服务端上下文。

## 5. 已知遗留（本次未做，避免范围蔓延）

1. **音素级口型**：见 3.3。
2. **全双工 / 回声消除**：见 2.4。
3. **线程内使用请求级 DB Session**：语音 worker 沿用请求级 Session（WS 连接内同一时刻只有一个
   worker 在用），收尾改为 `worker.join(timeout=5)` 后再关闭会话；更彻底的做法是 worker 自建
   Session，但会与测试的 `get_db` 覆盖机制冲突，收益不足以承担这个改动面。
4. **无跨会话长期记忆**：仅会话内 3 轮上下文，无学生长期记忆提炼。
5. **未做音色克隆**：仍为 edge-tts 在线音色（丢网降级为纯文字）。
